SREGym tests agents on their ability to diagnose and mitigate incidents in running applications. In an [earlier post](https://www.sregym.com/blog/jev-driven-sre-diagnosis), we tried a different approach to diagnosis. Instead of having an LLM agent investigate the incident, a diagnosis pipeline collects cluster evidence programmatically. A decision model, such as TypeSafe's Jev, then answers a few multiple-choice questions about it. It picks from the given options and returns a probability for each one. The pipeline uses its choices and the collected evidence to assemble a diagnosis report.

The first version of our pipeline (v1) succeeded about as often as a frontier LLM agent (Codex + GPT-5.6 Sol-medium), at about 1/200 of the cost. That experiment also made it clear how much a decision model depends on the pipeline around it. The model can only choose from what the pipeline shows it.

In this post, we introduce v1.1, an improved version of the pipeline. We traced failed v1 diagnoses and used what we learned to improve how the pipeline uses the model's answers, presents evidence, and builds requests.

We tested both versions with ten decision models on 37 problems: the 21 SREGym-Lite problems and 16 drawn at random from the rest of SREGym. The average pass rate rose from 59% to 73%.

## How v1 makes a diagnosis

The v1 pipeline collects evidence across the application and asks the model to rank possible origins of the failure. It then gathers more evidence for individual candidates and asks whether each is the origin, a victim of a failure elsewhere, unrelated, or undetermined.

The pipeline can stop when the model assigns a component an origin probability of at least 0.6. If no candidate meets that threshold, it uses fallback rules that can ultimately return to the initial ranking. For more details, see our [original blog post](https://www.sregym.com/blog/jev-driven-sre-diagnosis).

## Where v1 can go wrong

Take the deleted-account problem (`storage_user_unregistered-1`). SREGym deletes a user account from `mongodb-geo`, a database in a hotel-booking application called Hotel Reservation. The `geo` service uses this account to log in to the database. Without it, `geo` cannot log in and crashes. The database keeps running and logs the failed logins. The visible failure is in `geo`, but the missing account is in the database.

All ten models failed this problem with v1. In one diagnosis, the model initially ranked `geo` first. After examining the components, it gave the database an origin probability of 0.28 and `geo` a probability of 0.12. Neither reached 0.6, so the pipeline used its fallback rules. They chose `geo`, even though the model's later answers gave the database the higher origin probability.

Across the ten models, the fallback rules chose `geo` four times. More broadly, about a third of v1's diagnoses ended with the fallback rules, and only one in three of those passed.

## What v1.1 introduces

### Comparing possible causes

v1.1 compares the candidates it has examined to choose the final cause. Each candidate's score starts with the model's probability that it is the origin. Evidence from a failing component that calls it can raise that score.

If the model judges the failing component to be a victim and chooses the candidate as the next component to examine, the pipeline multiplies the probabilities of those two answers. It compares this value with the candidate's own origin probability and keeps the higher one.

<PipelineScoringEquations />

In a run on Astronomy Shop's `valkey_auth_disruption` fault, the `cart` service could not connect to its database, `valkey-cart`. Jev judged `cart` a victim with probability 0.90. It also chose `valkey-cart` as the next component to examine with probability 0.97. The pipeline multiplies these values to get 0.90 * 0.97 = 0.873. It uses that value as `valkey-cart`'s score because it is higher than its own origin probability of 0.61.

This helps the pipeline consider a component as a possible cause when its own origin probability is low but errors from other components point to it.

### Testing service connections

v1.1 also checks a connection from the component whose calls are failing. It tests whether the destination's name resolves and whether a connection can be established.

In Social Network's missing-Service problem, SREGym deletes the `user-service` Kubernetes Service, which provides an address for reaching the `user-service` pods. The pods keep running, but `compose-post-service` can no longer reach them through that address.

The checks reveal that the name does not resolve and the Service is missing. All ten v1 diagnoses failed, usually blaming the Deployment. With v1.1, seven pass.

### Keeping error details

Choosing a component is only part of the diagnosis. SREGym's LLM judge also checks how well the report explains what went wrong.

In six of the ten v1 diagnoses of the deleted-account problem, the reports named the database but did not explain why `geo` could not log in. Instead, they included the database's setup script. The log lines were also cut off before they showed why the login failed.

v1.1 puts the error and its reason first in the log lines. Every v1.1 report on this problem includes the missing-user error `Authentication failed; error=UserNotFound: Could not find user "admin"`. Nine of the ten diagnoses pass. The tenth includes the error but still falls short of explaining the cause.

All ten models passed more of the 37 problems with v1.1. The average pass rate rose from 59% to 73%. Every model also improved on the 16 randomly selected problems.

Since v1.1 does more work, the mean inference cost also increased. For Jev, it rose from 0.15 cents with v1 to 0.35 cents with v1.1.

## Next Steps

Seven problems still defeated every model. In the search-rate retry collapse fault, `search` keeps retrying requests to `rate` after they time out. Those retries keep `rate` overloaded even after traffic returns to normal. The reports usually blame the `rate` service without explaining how `search` keeps the failure going.

Next, we want to test whether records of individual requests and metrics over time could help the model make that connection. The decision model could also help choose what evidence the pipeline collects next.

We’d like to test the pipeline on harder SREGym problems, including hardware faults and metastable failures that continue after their trigger is gone. **Can it diagnose these incidents as well as frontier LLM agents for a fraction of a cent per diagnosis?**
